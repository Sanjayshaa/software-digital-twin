**System**: TwinCore Software Digital Twin

## 1. Research Questions & Formal Hypotheses

### Research Questions:
1. **$RQ_1$ (Efficacy)**: Does the multi-hop, typed relationship propagation of the Software Digital Twin achieve higher recall and F1-score in identifying truly affected software entities than simpler baselines (changed files set, 1-hop import closure, 1-hop call closure)?
2. **$RQ_2$ (Evidence Completeness)**: What proportion of change impact findings generated by the Digital Twin are accompanied by machine-verifiable, unbroken causal evidence paths against PostgreSQL relational rows?
3. **$RQ_3$ (Safety in Test Selection)**: Does separating epistemic uncertainty (`UNKNOWN_COVERAGE`) from proven invariance (`UNAFFECTED`) prevent test skipping on untested codebases?

### Hypotheses:
- **$H_1$**: Naive changed-file diffing achieves high precision on direct changes ($P \approx 1.0$), but severely degrades in recall ($R < 0.35$) on multi-tier architectures due to blind spots in transitive callers, API consumers, and test suites.
- **$H_2$**: Full Digital Twin analysis recovers $> 85\%$ of transitive affected entities while retaining $> 80\%$ precision through typed rule filtering and depth bounding.
- **$H_3$**: The safe test selection policy (`RUN = AFFECTED + UNKNOWN`, `SKIP = UNAFFECTED`) eliminates regression escapes while providing measurable test suite reduction ($> 30\%$) on well-mapped codebases.

## 2. Ground-Truth Taxonomy & Independence Invariants

A central methodological foundation of Phase 8.9 and 8.9.1 is the **rejection of the "changed files = ground truth" fallacy** and the **strict prohibition of circular self-evaluation**.

If a developer modifies `TaxService.ts` and causes a regression in `CheckoutController.ts`, `CheckoutController.ts` was not modified in the commit, but is **genuinely affected**. Equating changed files to ground truth falsely penalizes the Twin for identifying real dependents. Conversely, evaluating the Twin against its own predicted output creates circular target leakage ($P=1.0, R=1.0, F1=1.0$), which is scientifically invalid.

### Ground-Truth Provenance Sources:
| Source | Definition | Source Evidence |
| :--- | :--- | :--- |
| **`PATCH`** | Entities directly added, modified, or deleted in the Git patch (PARTIAL ONLY). | `git diff-tree`, AST symbol comparison. |
| **`TEST`** | Test cases that fail when the change is executed without downstream updates, or test cases explicitly written to verify the modified units. | Test execution runners (Jest, pytest, Vitest). |
| **`RUNTIME`** | Entities that emit error spans, latency spikes, or uncaught exceptions correlated with the deployment of the change. | OpenTelemetry spans, Sentry incidents. |
| **`MANUAL`** | Manually curated, peer-reviewed impact labels determined by senior software architects independent of Twin propagation. | Formal code review / architectural inspection. |
| **`EXTERNAL`** | External curated defect benchmarks (Defects4J, BugsInPy, SWE-bench). | Peer-reviewed benchmarks. |
| **`UNKNOWN`** | Ambiguous or unverified provenance. Accuracy calculation is refused. | Unverified sources. |

### Ground-Truth Independence Invariant:
$$\text{ground\_truth\_independent\_of\_twin} == \text{True}$$
If any ground-truth item originates from `ImpactPropagator`, `ImpactFinding`, `Twin Knowledge`, `Twin impact paths`, `Twin relationship traversal`, or `Full Twin output`, the metrics engine aborts calculation and returns:
$$\text{status} = \text{MetricStatus.INVALID\_GROUND\_TRUTH}$$

## 3. The Three Formal Evaluation Modes

To prevent invalid or misleading research claims, evaluations are partitioned into three mutually exclusive modes:

1. **Mode A: `PATCH_ONLY`**
   - Measures whether predictions overlap directly modified entities from the commit diff.
   - Status: `MetricStatus.PARTIAL_PATCH_ONLY`.
   - Explicit disclaimer: Does NOT represent complete change impact accuracy.
2. **Mode B: `INDEPENDENT_LABELS`**
   - Evaluates predictions strictly against independently obtained test failures, runtime telemetry, or manual architect annotations.
   - Status: `MetricStatus.VALID`. Only this mode can support scholarly claims regarding multi-hop impact detection.
3. **Mode C: `NO_GROUND_TRUTH`**
   - Executes baseline and Twin algorithms and reports prediction sets, path counts, and latency only.
   - Status: `MetricStatus.NO_GROUND_TRUTH`. Omits Precision, Recall, and F1-Score.

## 4. Mathematical Metric Formulations

To prevent mathematical distortion and reporting bias, metrics are computed with explicit zero-denominator handling:

### 1. Precision:
$$\text{Precision} = \begin{cases} \frac{\text{TP}}{\text{TP} + \text{FP}} & \text{if } \text{TP} + \text{FP} > 0 \\ 0.0 & \text{otherwise (Undefined)} \end{cases}$$

### 2. Recall:
$$\text{Recall} = \begin{cases} \frac{\text{TP}}{\text{TP} + \text{FN}} & \text{if } \text{TP} + \text{FN} > 0 \\ 0.0 & \text{otherwise (Undefined)} \end{cases}$$

### 3. F1-Score:
$$\text{F1} = \begin{cases} 2 \cdot \frac{\text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}} & \text{if } \text{Precision} + \text{Recall} > 0 \\ 0.0 & \text{otherwise} \end{cases}$$

### 4. Evidence-Backed Path Completeness:
$$\text{Completeness} = \frac{\text{Valid Paths Backed by Relational Edges}}{\text{Total Propagation Paths}}$$
